# Дизайн кроссплатформенного сервиса загрузки видео с YouTube

Дата: 2026-10-06

## 1. Назначение

Продукт помогает пользователю получить локальный файл публичного видео YouTube для рабочей обработки. Основной сценарий состоит из пяти действий: вставить ссылку, проверить видео, выбрать разрешение, выбрать MP4 или MOV и скачать файл.

Приложение разворачивается одной командой через Docker Compose и одинаково работает на macOS и Windows. По умолчанию веб-интерфейс доступен только на локальном компьютере.

Пользователь самостоятельно отвечает за наличие прав на загрузку и использование материала. Продукт не обходит платный доступ, DRM или авторизацию.

## 2. Границы первой версии

### Поддерживается

- публичное завершённое видео по ссылке `youtube.com` или `youtu.be`;
- обычные видео и Shorts;
- получение названия, превью, длительности и доступных разрешений;
- выбор разрешения и контейнера MP4 или MOV;
- загрузка лучших совместимых видео- и аудиодорожек для выбранного разрешения;
- объединение дорожек без перекодирования;
- отображение подготовки файла и его скачивание;
- автоматический переход между механизмами при техническом сбое;
- очередь загрузок, выполняющая одну задачу одновременно;
- автоматическая очистка временных файлов.

### Не поддерживается

- cookies или вход в аккаунт YouTube;
- YouTube Premium;
- YouTube Studio и Google Takeout;
- приватные, платные, возрастные и регионально недоступные видео;
- плейлисты и пакетная загрузка;
- прямые трансляции, премьеры до завершения и запись эфира;
- извлечение аудио в отдельный файл;
- перекодирование, повышение разрешения или изменение частоты кадров;
- история загрузок и пользовательские аккаунты;
- публичное интернет-развёртывание без внешней авторизации и защиты.

## 3. Пользовательский интерфейс

Приложение содержит одну рабочую карточку.

1. Пользователь вставляет ссылку и нажимает «Проверить».
2. После анализа появляются название, превью, длительность и варианты разрешения.
3. Пользователь выбирает разрешение.
4. Пользователь выбирает MP4 или MOV среди доступных для этого разрешения контейнеров.
5. Кнопка «Скачать» запускает подготовку файла. Карточка показывает состояние очереди и прогресс.
6. Когда файл готов, браузер начинает его скачивание.

Для каждого варианта интерфейс показывает контейнер, видеокодек, частоту кадров и приблизительный размер, если источник сообщает достаточно данных. Недоступный контейнер отображается неактивным с объяснением причины.

Приложение не понижает разрешение и не меняет контейнер без явного выбора пользователя. Если выбранную комбинацию нельзя собрать без перекодирования, загрузка не начинается.

## 4. Архитектура

Система состоит из пяти частей:

1. **Web UI** — статический интерфейс и отображение состояния задачи.
2. **HTTP API** — проверка ссылок, выдача метаданных, создание задачи и передача готового файла.
3. **Download Orchestrator** — единая модель форматов, очередь, выбор адаптера, классификация ошибок и очистка.
4. **Адаптеры источника** — yt-dlp, Cobalt и YouTube.js, скрытые за единым интерфейсом.
5. **Media Processor** — FFmpeg/ffprobe для проверки потоков и объединения видео со звуком без перекодирования.

```text
Browser
  |
  v
Web UI + HTTP API
  |
  v
Download Orchestrator
  |-- yt-dlp + EJS + PO Token Provider
  |-- self-hosted Cobalt
  `-- YouTube.js
  |
  v
FFmpeg/ffprobe -> temporary file -> HTTP download -> cleanup
```

Backend и UI входят в основной контейнер приложения. Cobalt и основной PO Token Provider запускаются отдельными внутренними сервисами Docker Compose. Резервный браузерный PO Token Provider работает в основном контейнере с headless Chromium. Порты внутренних сервисов не публикуются на хост. Временные файлы хранятся в отдельном Docker volume.

## 5. Единый интерфейс адаптеров

Каждый адаптер реализует доступную ему часть контракта:

- `inspect(url)` возвращает нормализованные метаданные и варианты качества;
- `download(request, destination, progressCallback)` сохраняет выбранные дорожки или готовый файл;
- `health()` проверяет готовность зависимости;
- `cancel(jobId)` прекращает активную операцию и освобождает ресурсы.

Нормализованный вариант качества содержит высоту кадра, ширину, частоту кадров, HDR-флаг, видеокодек, аудиокодек, контейнеры без перекодирования, приблизительный размер и идентификаторы исходных потоков. Идентификаторы конкретного движка остаются внутри его адаптера.

## 6. Механизмы получения видео

### 6.1. Основной механизм: yt-dlp

yt-dlp используется первым для анализа и загрузки. В образ входят FFmpeg, ffprobe, поддерживаемый JavaScript runtime и EJS-компоненты, необходимые для актуальных JavaScript-проверок YouTube.

Для форматов, которым нужен Proof of Origin Token, рядом запускается `bgutil-ytdlp-pot-provider`, рекомендованный документацией yt-dlp. Если он не может выпустить гостевой токен, yt-dlp делает одну повторную попытку через экспериментальный `yt-dlp-getpot-wpc`, который использует headless Chromium и гостевую сессию. После отказа обоих провайдеров задача переходит к Cobalt. Ручной ввод токенов отсутствует. Cookies и данные аккаунта не передаются.

Версия yt-dlp фиксируется в образе для воспроизводимости. Обновление зависимости выполняется новой сборкой образа, а не самопроизвольным обновлением работающего контейнера.

Документация: [yt-dlp](https://github.com/yt-dlp/yt-dlp), [EJS](https://github.com/yt-dlp/yt-dlp/wiki/EJS), [PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide), [bgutil provider](https://github.com/Brainicism/bgutil-ytdlp-pot-provider), [browser provider](https://github.com/coletdjnz/yt-dlp-getpot-wpc).

### 6.2. Первый резерв: self-hosted Cobalt

Cobalt вызывается через внутренний HTTP API собственного контейнера. Публичные Cobalt-инстансы не используются. Координатор передаёт ссылку и выбранное разрешение, затем сохраняет результат в зависимости от типа ответа Cobalt. Для MP4 запрашивается H.264 и MP4. Для MOV запрашивается совместимый H.264-поток, после чего Media Processor проверяет кодеки через ffprobe и выполняет локальный remux в MOV без перекодирования. Если Cobalt не вернул точное разрешение или совместимые кодеки, попытка считается технически неудачной и координатор переходит к YouTube.js.

Cobalt уже использует YouTube.js, поэтому этот путь не считается полностью независимым от следующего адаптера. Он полезен благодаря собственной логике выбора потоков, туннелирования и обработки медиа.

Код Cobalt работает отдельным сервисом. Изменения его исходного кода не планируются. При изменении или распространении сборки должны выполняться требования AGPL-3.0.

Документация: [Cobalt API](https://github.com/imputnet/cobalt/blob/main/docs/api.md), [Cobalt repository](https://github.com/imputnet/cobalt).

### 6.3. Второй резерв: YouTube.js

Прямой адаптер YouTube.js получает данные через внутренний API YouTube, выбирает совместимые потоки и передаёт их Media Processor. Он не использует cookies аккаунта и не пытается получать закрытый контент.

Этот механизм запускается последним, поскольку Cobalt также зависит от YouTube.js и оба пути могут одновременно перестать работать при изменении YouTube.

Документация: [YouTube.js](https://github.com/LuanRT/YouTube.js).

## 7. Анализ ссылки и выбор качества

Сначала координатор проверяет схему, хост и структуру URL. Разрешены только `https`-ссылки на известные домены YouTube; редиректы на другие домены не передаются адаптерам.

Основной вызов `inspect` выполняет yt-dlp. Если он завершается технической ошибкой, используется YouTube.js. Cobalt не является источником полного списка исходных форматов: его API принимает целевое разрешение, поэтому он применяется прежде всего на стадии загрузки.

Для каждого фактически доступного разрешения координатор строит варианты MP4 и MOV. Вариант существует только тогда, когда выбранные видео- и аудиодорожки можно объединить в контейнере без перекодирования. Среди совместимых дорожек выбираются максимальные битрейт и качество звука при точном совпадении выбранного разрешения.

FFmpeg запускается в режиме stream copy. Изменение кодека, разрешения, HDR, частоты кадров или качества запрещено. Если muxing завершается ошибкой совместимости, координатор не запускает транскодирование.

## 8. Выполнение и автоматический fallback

Для загрузки используется порядок:

1. yt-dlp;
2. Cobalt;
3. YouTube.js.

Переход к следующему адаптеру разрешён только при технических ошибках: временная недоступность механизма, несовместимый ответ, ошибка получения потока, HTTP 403/429 от медиасервера, истечение URL потока или внутренняя ошибка адаптера.

Следующий адаптер обязан сохранить выбранные пользователем разрешение и контейнер. Перед стартом он заново подтверждает наличие точной комбинации. Если подтверждения нет, задача завершается понятной ошибкой без скрытой замены формата.

Fallback не выполняется для окончательных ошибок:

- ссылка не относится к поддерживаемому YouTube URL;
- видео удалено, приватно, требует входа, ограничено по возрасту или региону;
- идёт прямая трансляция;
- выбранная комбинация качества и контейнера отсутствует;
- недостаточно свободного места;
- пользователь отменил задачу.

Координатор хранит технические причины всех попыток в локальном журнале, но UI показывает одну понятную итоговую ошибку без внутренних команд и токенов.

## 9. Очередь, прогресс и хранение файлов

В первой версии одновременно выполняется одна задача. Новая задача получает позицию в очереди. Состояния задачи:

- `queued`;
- `downloading`;
- `merging`;
- `ready`;
- `failed`;
- `cancelled`;
- `expired`.

Прогресс передаётся в UI через Server-Sent Events. Если адаптер не сообщает точный объём, интерфейс показывает этап без фиктивного процента.

Перед загрузкой координатор сравнивает оценочный размер с доступным местом и сохраняет резерв для объединения потоков. Если размер неизвестен, свободное место контролируется во время записи.

Готовый файл получает безопасное имя на основе названия и идентификатора видео. После успешной HTTP-передачи файл удаляется. Если браузер не забрал файл, задача и её файлы истекают через 60 минут. При старте приложения удаляются оставшиеся файлы незавершённых и истёкших задач.

Постоянная база данных не нужна. Состояние очереди хранится в памяти; временный manifest в каталоге задачи нужен только для корректной очистки после перезапуска.

## 10. HTTP API

- `POST /api/inspect` — принимает YouTube URL и возвращает метаданные с нормализованными вариантами качества;
- `POST /api/jobs` — создаёт задачу для точного разрешения и контейнера;
- `GET /api/jobs/:id` — возвращает текущее состояние;
- `GET /api/jobs/:id/events` — поток событий прогресса;
- `GET /api/jobs/:id/file` — передаёт готовый файл;
- `DELETE /api/jobs/:id` — отменяет задачу и удаляет её файлы;
- `GET /health` — состояние приложения и внутренних зависимостей.

API принимает только JSON ограниченного размера. Идентификаторы задач случайны и не содержат путей к файлам. Пользовательский ввод никогда не подставляется в shell-команду: процессы запускаются массивом аргументов без shell.

## 11. Безопасность и эксплуатационные ограничения

- По умолчанию основной порт привязан к `127.0.0.1`.
- Доступ из локальной сети включается явной переменной конфигурации.
- Cobalt и PO Token Provider доступны только во внутренней Docker-сети.
- Backend не загружает произвольные URL и повторно проверяет хост после редиректа.
- В имена файлов не попадают управляющие символы и компоненты пути.
- Для анализа ссылок и создания задач действует локальное ограничение частоты запросов.
- Логи не содержат полных временных URL медиапотоков, токенов или заголовков авторизации внутренних сервисов.
- Контейнер приложения работает без root, где это поддерживается базовым образом, и имеет запись только во временный volume.

Публичное размещение потребует отдельного проекта: аутентификации, HTTPS, квот, сетевой фильтрации, ограничений размера и мониторинга злоупотреблений.

## 12. Развёртывание

Пользователь устанавливает Docker Desktop, открывает каталог проекта и запускает:

```bash
docker compose up -d
```

После прохождения health checks интерфейс доступен по адресу `http://localhost:8080`. Compose-файл содержит основной сервис, Cobalt и `bgutil-ytdlp-pot-provider`, их health checks, внутреннюю сеть и временный volume. Основной образ включает headless Chromium и резервный браузерный провайдер.

README содержит одинаковый основной сценарий для macOS и Windows, команды просмотра журналов, обновления образов и остановки сервиса. Архитектуры `linux/amd64` и `linux/arm64` должны собираться и запускаться, чтобы поддержать Windows x64 и современные Mac на Apple Silicon.

## 13. Обработка ошибок в интерфейсе

Пользователь получает сообщения, привязанные к действию:

- «Проверьте ссылку на видео YouTube»;
- «Видео недоступно без входа в аккаунт»;
- «Видео ещё транслируется»;
- «Выбранный формат больше недоступен — проверьте ссылку заново»;
- «Недостаточно места для подготовки файла»;
- «YouTube временно отклонил запрос. Попробуйте позже»;
- «Не удалось подготовить файл ни одним доступным способом».

При смене адаптера UI продолжает показывать подготовку файла и не раскрывает внутреннюю реализацию. Итоговая ошибка может содержать короткий код для поиска соответствующей записи в локальном журнале.

## 14. Тестирование

### Модульные тесты

- нормализация и проверка допустимых YouTube URL;
- преобразование форматов каждого адаптера в единую модель;
- выбор лучшей совместимой комбинации для разрешения и контейнера;
- классификация технических и окончательных ошибок;
- порядок fallback без скрытой смены выбора;
- безопасные имена файлов и расчёт срока хранения.

### Интеграционные тесты

- заглушки трёх адаптеров проверяют успешный основной путь и каждый переход;
- FFmpeg объединяет небольшие тестовые дорожки в MP4 и MOV через stream copy;
- несовместимые кодеки отклоняются без запуска перекодирования;
- очередь допускает только одну активную задачу;
- отмена, ошибка и перезапуск очищают временные данные;
- HTTP API и Server-Sent Events согласованно отражают состояния задачи.

### Smoke-тесты

- Docker Compose поднимается одной командой и проходит health checks;
- короткое публичное тестовое видео анализируется и скачивается в доступном MP4;
- MOV проверяется на видео с совместимыми дорожками;
- готовые файлы воспроизводятся, содержат видео и звук и имеют выбранное разрешение;
- сборка проверяется для `linux/amd64` и `linux/arm64`.

Онлайн smoke-тесты запускаются отдельно от стабильного набора, поскольку доступность конкретного видео и поведение YouTube могут измениться независимо от кода.

## 15. Критерии приёмки

Первая версия считается готовой, когда:

1. На macOS и Windows сервис запускается документированной командой Docker Compose.
2. Пользователь проходит полный сценарий без дополнительных настроек и аккаунта.
3. UI показывает только реально доступные разрешения и совместимые MP4/MOV.
4. Загруженный файл содержит звук, точное выбранное разрешение и исходные кодеки без перекодирования.
5. При смоделированном техническом отказе координатор последовательно пробует все три механизма.
6. Окончательная ошибка не вызывает бессмысленные повторные попытки.
7. После скачивания, отмены, ошибки, истечения срока и перезапуска временные файлы удаляются.
8. Внешние URL, shell-инъекции и выход за временный каталог блокируются.
9. Стабильный автоматический набор тестов проходит без обращения к YouTube; отдельный онлайн smoke-тест подтверждает актуальную совместимость.

## 16. Известные ограничения

YouTube меняет внутренние API, JavaScript-проверки и требования к PO-токенам. Поэтому ни один из механизмов не гарантирует постоянную загрузку любого публичного видео. yt-dlp, Cobalt, YouTube.js и PO Token Provider должны обновляться регулярными пересборками после проверки smoke-тестом.

Cobalt и прямой адаптер YouTube.js частично разделяют одну технологическую зависимость. Их последовательное использование повышает шанс успешной обработки разных ответов и форматов, но не обеспечивает полную независимость резервных путей.
